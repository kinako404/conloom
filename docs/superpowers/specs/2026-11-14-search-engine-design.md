# 内置搜索引擎（长期回忆）设计

日期：2026-11-14
状态：已定稿，待实施
上位文档：总设计 §7.3（消息片段与混合检索）；技能设计 `2026-11-13-skills-design.md`

## 1. 为什么做

- 现在的 `recall` 只扫描最近 5000 条，用关键词子串匹配：几个月前的事查不到，换个说法（"出去玩"对"旅游"）也查不到。
- 实测（2026-11-14）：
  - 项目用的纯 Go SQLite（modernc，SQLite 3.54）支持 FTS5 和 bm25。30 万条消息里，在单个会话的 10 万条中做全文检索约 70ms，写入加建索引每条约 2ms。
  - bge-m3 已部署在向量主机上：Ollama，纯 CPU，双路至强服务器，单句约 50ms，1024 维。语义匹配有效，例如"出去玩"能命中"周末打算出门逛逛"（0.82）。
  - ConLoom 通过专用 SSH 隧道访问它：`127.0.0.1:11434`，OpenAI 兼容的 `/v1/embeddings`，单次往返约 440ms，其中网络约 184ms。

## 2. 目标、非目标、反目标

**目标**

1. **关键词索引**：每条消息入库时同步写入 FTS5 索引。中文按相邻两字切词，英文和数字按词切词并转成小写。历史消息在后台补建索引。`recall` 能查到会话的全部历史，按 bm25 排序。
2. **语义检索（可选）**：配置了向量模型时，把会话按段切开，生成向量，在后台增量处理。`recall` 同时做向量检索，和关键词结果融合。没配置或者服务不可用时，自动退回纯关键词检索。
3. **可切换模型**：默认 bge-m3。改配置里的模型名以后，后台对所有段重新生成向量；新向量没补完之前，旧模型的向量不参与检索（维度不同，不能混用）。
4. **时间范围**：`recall` 新增可选的 `after` 和 `before` 参数（YYYY-MM-DD，按 `server.timezone` 解释），用来查"几个月前""去年夏天"这类问题。
5. **流水表清理**：任务、发件箱、事件等运维数据定期清理。聊天原文 `messages` 作为长期记忆的来源，不清理。

**非目标**

- 跨会话检索（QQ 和 Telegram、群聊和私聊互不相通）。
- 按月写小结（L3 摘要），以后再做。
- 外部向量数据库：向量放在 SQLite 里，内存里暴力计算余弦相似度。
- GPU 推理：向量主机的显卡留给 vLLM。

**反目标**

- 检索结果泄露别的会话的内容、ID、联系方式，或者被忘记的内容。现有 `recall` 的所有过滤规则必须同样作用在新路径上。
- 后台补建索引、生成向量影响在线回复：要低优先级、限速、分批，失败了退避，不阻塞写入。
- 向量服务挂掉时，`recall` 报错或者变慢。必须有超时，并退回关键词检索。
- 换模型以后，新旧向量混在一起比较。

## 3. 方案取舍

| 方案 | 结论 |
|---|---|
| **FTS5 + 自己预先切词（选用）** | 把两字切词的结果用空格连起来，交给 unicode61 分词器建索引，自带 bm25。纯 Go 就能用 |
| FTS5 trigram 分词器 | 中文两字词最常见，trigram 至少要三个字，查不到，不用 |
| 自建倒排表 | 要自己算 bm25，没有必要 |
| **向量放 SQLite + 内存暴力检索（选用）** | 1 万段 × 1024 维只要几毫秒；不需要新组件 |
| 外部向量库（pgvector、qdrant 等） | 规模用不上，还多一个运维对象 |
| **按段生成向量（选用）** | 一段是连续几条消息，带上下文，语义更完整，向量也少 |
| 每条消息单独生成向量 | 一句"好呀"没有语义，数量还多 10 倍 |

## 4. 设计

### 4.1 关键词索引（任务 A）

- **迁移 `0006_message_fts.sql`**：建一张 FTS5 虚拟表 `message_fts(seg)`，rowid 等于 `messages.seq`，分词器 unicode61。`seg` 的内容是：一个会话标记（会话键哈希后的 `c<hex>`）、正文切出的词、发言人显示名切出的词，用空格连接。
- **入库**：消息写入 `messages` 的同一个事务里写入 `message_fts`。机器人消息也要写入，查询时再过滤。
- **补建**：启动后在后台从旧到新，分批（每批 500 条）补建还没有索引的消息。用一个进度标记记录补到哪条 seq。补建期间新消息照常写入。
- **查询**：
  - store 新增 `SearchMessages(ctx, convKey string, terms []string, r search.Range, limit int) ([]store.MessageHit, error)`。
  - MATCH 写成 `c<hex> AND (t1 OR t2 …)`，按 bm25 排序，再按时间范围过滤。
  - 返回 seq 和分数。
- **切词**：复用 `recall` 现有的切词逻辑：汉字两字一组，英文和数字成词，keywords 里的中文整词也算一个词。抽成公共函数，入库和查询用同一套。

### 4.2 语义检索（任务 B）

**配置**

```yaml
embedding:            # 可选；不配置就只用关键词检索
  endpoint: http://127.0.0.1:11434/v1
  model: bge-m3
  api_key: ""          # 可选
  timeout: 10s
  batch_size: 16
```

**切段**

- 按会话分段：同一段内相邻消息的间隔不超过 30 分钟；一段最多 8 条消息，或者约 400 字。
- 段落文本用第三人称记录格式写，每行 `[MM-DD HH:MM] 名字：正文`，不带任何 ID。
- 写进段落之前做和 `recall` 一样的过滤：命令和机器人对命令的回复不收；联系方式打码；过一遍审查；被忘记的人在忘记时间之前的消息不收。
- 一段"关闭"以后才生成向量：再来一条消息时会超出这一段的上限，或者距这一段最后一条消息已超过 30 分钟。还没关闭的最后一段，在检索时由关键词路径覆盖。

**存储（迁移 `0007_memory_chunks.sql`）**

表 `memory_chunks`，列为：

- `id`
- `conversation_key`
- `start_seq`、`end_seq`
- `start_at`、`end_at`
- `text_hash`
- `model`
- `dims`
- `vector`（float32 小端 BLOB）
- `created_at`

索引建在 `(conversation_key, end_seq)` 和 `(model)` 上。

**后台生成向量**

- 挂在维护循环上，每分钟一轮。
- 找出每个会话里还没被切段覆盖的已关闭消息，切段后批量请求向量服务，每批 `batch_size` 段。
- 每轮最多处理 200 段，避免长时间占用。
- 失败时指数退避，最长 10 分钟。
- 只对**记忆已生效**（`memory.enabled && allow_long_requests`）的会话生成向量。

**换模型**

配置里的 model 和库里的 model 不一致时，旧向量不参与检索，后台按会话从新到旧重新生成。全部完成后删除旧模型的向量。

**检索**

- 实现 `search.VectorSearcher` 接口。
- 先把查询句转成向量：用短超时，默认 2 秒，超时就返回空结果，不报错。
- 再对会话里所有当前模型的段计算余弦相似度，按时间范围过滤，取前 N 个。
- 每个会话的向量缓存在内存里，最多缓存 8 个会话，按 LRU 淘汰；有新段写入时更新缓存。

**忘记**

- 私聊 `/忘记我`：删除这个会话在忘记时间之前的全部段。
- 群聊 `/忘记我`：删除含有这个人在忘记时间之前消息的段，并把它们标记为待重建。重建时这个人的那些消息不再收进段落。
- 和现有的 `Forget` 写在同一个事务里，或者紧接着执行；失败要能重试，不能让被忘记的内容留在向量里。

### 4.3 `recall` 融合（任务 A）

- **新增参数** `after`、`before`（可选，格式 YYYY-MM-DD，按 `server.timezone` 解释，`before` 当天也包括在内），并写进 Spec 的描述里，引导模型在用户提到时间时使用。
- **两路检索**：
  - 关键词：`SearchMessages` 取前 50 条消息；
  - 语义：`VectorSearcher.Search` 取前 20 段，没有配置时跳过。
- **融合**：用 RRF（k=60）。消息命中按单条计分，段命中按整段计分；命中重叠的合并成一组。再轻度考虑时间：越新的略加分，权重很小，以相关度为主。
- **输出**：
  - 每组展开成"命中消息加前后各 2 条"，或者"整段"，按时间排序；
  - 过滤、打码、审查、无 ID、上限 1500 字等规则全部沿用现有实现；
  - 每组前面加一行日期标题，例如 `—— 2026-03-02 ——`，让模型知道这是哪天的事。
- **不再只看最近 5000 条**；删掉"最近 5000 条"这一路径，以及相关的常量和文档。
- **接口**（提前提交到 `internal/search/search.go`）：

```go
type Range struct{ After, Before time.Time } // 零值表示不限
type Hit struct {
    FromSeq, ToSeq int64
    Score          float64
}
type VectorSearcher interface {
    Search(ctx context.Context, convKey, query string, r Range, limit int) ([]Hit, error)
}
```

### 4.4 流水表清理（任务 C）

- 新增 `runtime.ops_retention`，默认 `720h`（30 天），范围 24h–8760h。
- 维护循环每小时清理一次，每次限量删除，避免长事务：
  - 终态的 `tasks`；
  - 已确认或已过期的 `outbox_actions`；
  - `audit` 另有 `runtime.audit_retention`，默认 2160h（90 天）。
- **不清理** `messages`、记忆表、群策略和人格版本。
- 先确认 `messages` 和这些表之间没有外键或代码依赖。比如 reply_to 解析、恢复任务时会不会读到旧任务，要核实。
- 日志：每轮记一行清理条数。

### 4.5 可观测性

指标：

- `conloom_search_seconds{path="keyword|vector"}`
- `conloom_embedding_requests_total{result}`
- `conloom_embedding_backlog`：还没生成向量的已关闭段数
- `conloom_fts_backfill_remaining`
- `conloom_cleanup_deleted_total{table}`

## 5. 我做的决定（可以推翻）

- 默认 bge-m3。模型可以通过配置切换；切换后后台重新生成向量，期间这部分语义检索暂不可用。
- 只给记忆已生效的会话生成向量。
- 切段规则：间隔不超过 30 分钟、最多 8 条或约 400 字。
- 用 RRF 融合，时间只做轻度加权。
- `messages` 永不清理，运维表保留 30 天，审计保留 90 天。
- 向量服务通过 SSH 隧道接入，配置里写本机地址。隧道的部署方式写进 docs/deployment.md，但只写通用步骤，不写真实主机名。

## 6. 测试要点

- **FTS**：
  - 切词和入库同步；
  - 补建可以中断、可以续做；
  - 会话隔离（会话标记）；
  - 时间范围；
  - bm25 排序；
  - 已有数据的库可以迁移，也能回滚到旧版本二进制。
- **向量**：
  - 用假的向量服务（httptest），覆盖切段规则、段落文本的过滤和打码、批量请求、失败退避、只处理记忆已生效的会话；
  - 换模型后重新生成向量，旧向量不参与检索；
  - 两种忘记都会删除对应的段，群聊的段会重建；
  - 查询超时时退回关键词检索；
  - 内存缓存会随新段更新。
- **recall**：
  - 两路结果融合；
  - 只有关键词时照常工作；
  - after/before 生效；
  - 日期标题；
  - 所有既有的隐私断言继续通过；
  - 很早以前的消息能被查到（超出原来 5000 条的范围）。
- **清理**：
  - 只删已过期的终态数据；
  - 限量；
  - 不碰 `messages`；
  - 恢复任务不受影响。
